3. 공통 API 클라이언트

파일: lib/api-client.ts 29~40행

      ...init,
      headers: isFormData

줄별 해설

- fetch가 실제 네트워크 요청을 수행한다.
- ...init은 호출자가 지정한 method와 body를 복사한다.
- FormData가 아니면 JSON Content-Type을 자동으로 넣는다.
- 응답을 먼저 text로 읽는 이유는 서버가 항상 JSON을 준다고 보장할 수 없기 때문이다.
- 예를 들어 플랫폼의 413 응답이나 게이트웨이 HTML 오류는 JSON이 아닐 수 있다.
- JSON.parse가 실패해도 즉시 앱 전체가 깨지지 않도록 try/catch로 감싼다.

4. 서버 응답 상태 처리

파일: lib/api-client.ts 44~55행

    const error = (json as { error?: unknown } | null)?.error;

    if (!res.ok) {
      if (typeof error === 'string') throw new Error(error);
      if (res.status === 413) throw new Error(tooLargeError);
      throw new Error(fallbackError);
    }

    if (json === null && text) throw new Error(fallbackError);
    return json as T;

- res.ok는 상태 코드가 200~299인지 알려준다.
- 실패 응답에 문자열 error가 있으면 그 문구를 화면 쪽 catch로 전달한다.
- 413은 요청 본문이 너무 큰 경우이므로 별도 안내를 만든다.
- 성공으로 표시됐지만 JSON이 아니면 계약 위반으로 보고 오류를 낸다.
- 마지막 타입 단언은 런타임 검사가 아니다. 서버가 잘못된 JSON을 보내도 자동 검증하지 않는다.

상태 코드 읽는 법

- 200: 정상 조회·수정
- 201: 새 리소스 생성 성공
- 400: 입력값 또는 비즈니스 규칙 위반
- 401: 로그인 필요 또는 로그인 정보 불일치
- 403: 로그인은 했지만 해당 데이터에 접근 권한 없음
- 404: 대상 데이터 없음
- 409: 현재 상태와 충돌
- 413: 업로드 본문이 너무 큼
- 429: 너무 많은 시도 또는 사용량 제한
- 500: 서버 코드, DB, 외부 서비스 문제

장애 점검 순서

1. 브라우저 개발자 도구 Console에 빨간 오류가 있는지 본다.
2. Network 탭에서 해당 요청이 실제로 생성됐는지 본다.
3. Request Payload가 기대한 키와 값인지 본다.
4. Status와 Response 내용을 확인한다.
5. 요청이 없으면 React 이벤트, 있으면 API Route부터 추적한다.

AI 수정 검증 기준

- 오류를 없애려고 catch를 비워 버리지 않았는가?
- 실패 상태인데도 성공 화면으로 진행하지 않는가?
- JSON 요청인데 Content-Type이나 JSON.stringify를 빠뜨리지 않았는가?
- FormData 요청에 application/json을 강제로 붙여 업로드를 깨뜨리지 않았는가?

학습 목표

- useState가 화면 값과 로딩 상태를 어떻게 보관하는지 안다.
- 비동기 처리의 try/catch/finally 역할을 구분한다.

3. 반드시 정리되는 finally

파일: app/student/page.tsx 471~477행

    } catch (err) {
      setError((err as Error).message);
      clearNoticeLater();
    } finally {
      setLoginLoading(false);
      setBootLoading(false);
    }
  };

- catch는 api()가 throw한 오류를 받아 사용자 문구로 저장한다.
- finally는 성공과 실패 어느 쪽에서도 실행된다.
- 로딩 상태를 finally에서 해제해야 실패 후 버튼이 영구 비활성화되는 버그를 막는다.
- err as Error는 타입 단언이다. 실제 값이 반드시 Error라는 런타임 보장은 아니다.

자주 발생하는 React 장애

- 무한 요청: useEffect 의존성에 렌더링마다 새로 생성되는 값을 넣은 경우
- 오래된 화면: 서버 작업 후 state를 갱신하거나 다시 조회하지 않은 경우
- 이중 제출: loading 상태로 버튼을 막지 않은 경우
- 깜빡임: 로그인 확인이 끝나기 전에 로그인 폼을 먼저 렌더링한 경우
- 순서 경쟁: 느린 이전 요청이 빠른 최신 요청보다 늦게 도착해 상태를 덮는 경우

디버깅 방법

- React DevTools에서 state가 기대대로 변하는지 본다.
- Network의 요청 순서와 완료 시점을 비교한다.
- 로딩 시작, 요청 완료, catch, finally 지점에 임시 로그를 넣어 흐름을 좁힌다.
- setState 직후 콘솔에 이전 값이 찍힐 수 있음을 기억한다. 상태 변경은 다음 렌더에 반영된다.

- 서버 응답을 받기 전에 성공 상태로 바꾸지 않는가?

3강. TypeScript와 Zod: 타입 계약과 실제 입력 검증
######################################################################

학습 목표

- TypeScript 타입과 런타임 검증의 차이를 안다.
- as const, union 타입, Record가 데이터 오류를 줄이는 방식을 읽는다.
- Zod 검증 실패가 400 응답으로 연결되는 과정을 이해한다.

1. 허용된 감정값을 타입으로 만들기

파일: types/domain.ts 1~10행, 46~48행

export const EMOTION_TYPES = [
  'moved',
  'worried',
  'thankful',
  'curious',
  'longing',
  'joyful',
  'surprised',
  'affectionate',
  // ...중간 생략
] as const;
export type EmotionType = (typeof EMOTION_TYPES)[number];

- 배열은 서버와 화면이 공유하는 허용값 목록이다.
- as const가 없으면 각 항목이 넓은 string 타입으로 변할 수 있다.
- typeof EMOTION_TYPES[number]는 배열 항목 전체를 union 타입으로 만든다.
- EmotionType에는 'joyful' 같은 정의된 값만 들어갈 수 있다.
- DB의 emotion_type enum과 이 목록이 어긋나면 저장 오류가 생기므로 함께 관리해야 한다.

2. 학생 로그인 스키마

파일: lib/validators.ts 47~54행

export const studentLoginSchema = z.object({
  classCode: z
    .string()
    .trim()
    .regex(/^[0-9]{1,6}$/, '학급코드는 1~6자리 숫자여야 합니다.'),
  name: z.string().min(1).max(30),
  password: z.string().regex(
    STUDENT_PASSWORD_REGEX, '비밀번호는 숫자 4자리여야 합니다.'
  )
});

- z.object는 입력 전체가 객체이며 지정한 필드를 가져야 한다는 뜻이다.
- classCode는 문자열만 받고 공백을 제거한 뒤 정규식으로 검사한다.
- ^와 $는 문자열 전체가 규칙에 맞아야 한다는 의미다.
- 이름은 1~30자로 제한한다.
- 비밀번호 규칙은 lib/password.ts의 공통 상수를 사용한다.
- Zod는 실제 실행 중 외부 입력을 검사한다. TypeScript만으로는 이 역할을 못 한다.

    );
  }
  const classCode = parsed.data.classCode.trim();

- 잘못된 JSON이면 빈 객체로 바꿔 검증 실패 흐름으로 보낸다.
- safeParse는 예외 대신 success가 true/false인 결과를 준다.
- 실패하면 DB를 조회하지 않고 400으로 종료한다.
- 성공한 parsed.data는 스키마를 통과한 타입으로 좁혀진다.
- 이미 스키마에서 trim했으므로 마지막 trim은 중복이지만 결과는 안전하다.

TypeScript와 Zod의 경계

- TypeScript: 개발·빌드 시 코드 작성자의 실수를 잡는다.
- Zod: 브라우저, 외부 호출자, 변조된 요청처럼 실행 중 들어오는 값을 잡는다.
- api<ResponseType>()의 ResponseType은 서버 응답을 실제 검사하지 않는다.
- AI 응답, JSONB, request body에는 런타임 스키마가 특히 중요하다.

오류 상황과 디버깅

- 브라우저에는 맞아 보이는데 400: 공백, 숫자/문자 타입, 최대 길이를 확인한다.
- 프런트 타입은 통과하지만 DB 오류: DB enum·컬럼 제약과 코드 타입이 어긋났는지 본다.
- 스키마 변경 후 여러 API 실패: 공통 validators 변경 영향 범위를 rg로 검색한다.
- 오류 문구가 [object Object]: API 클라이언트가 문자열 error만 처리하는데 flatten 객체를 반환한 경로를 확인한다.

- 타입 오류를 없애려고 any를 추가하지 않았는가?
- 클라이언트 검증만 추가하고 서버 검증을 빠뜨리지 않았는가?
- 스키마의 최대 길이가 DB 컬럼 제한과 일치하는가?
- 새로운 enum 값이 타입, 화면 메타데이터, DB 마이그레이션 모두에 반영됐는가?

401과 403

- 401 Unauthorized: 누구인지 확인되지 않음. 다시 로그인해야 한다.
- 403 Forbidden: 누구인지는 알지만 그 대상에 접근할 권한이 없다.

- 운영에서만 로그인 유지 실패: HTTPS, secure, 도메인, SameSite 설정을 본다.
- 다른 반 데이터 노출: API에 requireTeacherClass/Student 검사가 있는지 본다.
- 학생 세션이 계속 401: DB의 token_hash와 만료 시간, 서버 시간대를 확인한다.
- 무한 로그인 반복: /me 요청의 401 처리와 화면의 세션 초기화 순서를 확인한다.

1. 학급과 학생의 관계

파일: supabase/schema.sql 59~76행

- UUID 기본키는 각 행을 고유하게 식별한다.
- classes.teacher_id는 teacher_profiles를 참조한다.
- students.class_id는 학생이 어느 학급에 속하는지 나타낸다.

- NOT NULL과 CHECK는 애플리케이션을 우회한 잘못된 저장도 DB에서 막는다.
- 실제 최신 구조는 이후 migrations가 schema.sql에 변경을 누적한 결과다.

2. 마음기록 조회 쿼리

- gte/lte는 서울 기준 하루의 시작과 끝 범위다.
- 최신순 정렬 후 한 건만 가져온다.
- maybeSingle은 0건이면 null, 1건이면 객체를 반환한다.
- 여러 건이 나오지 않도록 limit(1)을 먼저 적용했다.

DB 장애 점검

- column does not exist: 코드가 기대하는 마이그레이션이 운영 DB에 적용됐는지 확인한다.
- duplicate key: unique 제약과 중복 요청을 확인한다.
- foreign key violation: 부모 데이터 삭제 또는 잘못된 id 전달을 확인한다.
- RLS 오류: anon 사용자 쿼리인지 service role 쿼리인지 구분한다.
- 느린 조회: WHERE/JOIN에 쓰는 컬럼 인덱스와 반환 행 수를 확인한다.

마이그레이션 원칙

- 운영 DB를 schema.sql로 다시 만드는 것이 아니라 미적용 migration을 순서대로 적용한다.
- 컬럼 삭제나 타입 변경 전 코드 배포 순서와 기존 데이터 변환을 계획한다.
- 코드, 마이그레이션, 롤백 파일을 함께 검토한다.
- service role 키는 서버에서만 사용한다.

1. 배움성찰 상태는 파생값이다

/**
 * 미제출 / 제출 완료 / 평가 대기 / 피드백 완료를 가른다.
 */
export function getLearningStatus(
  submission: SubmissionStatusInput,
  grading?: GradingInput
): LearningStatus {
  if (!submission || submission.status !== 'submitted') return 'none';
  if (grading && grading.criteriaCount > 0) {
    return grading.gradedCount >= grading.criteriaCount ? 'reviewed' : 'grading';
  }
  return submission.feedback_text ? 'reviewed' : 'submitted';
}

- 화면의 네 상태가 DB의 단일 status 컬럼과 일대일 대응하지 않는다.
- 행이 없거나 draft이면 none이다.
- 평가요소가 있으면 모든 요소에 등급이 있어야 reviewed다.
- 평가요소가 없으면 서술 피드백 유무로 reviewed를 판단한다.
- 교사·학생 화면이 같은 함수를 쓰므로 서로 다른 상태를 보여줄 위험이 줄어든다.

export function isSubmittable(
  materialCount: number,
  questionCount: number,
  answers: (string | null | undefined)[],
): boolean {
  if (materialCount <= 0) return false;
  if (questionCount === 0) return true;
  if (answers.length < questionCount) return false;
  return answers.every(
    (answer) => (answer ?? '').trim().length > 0
  );
}

- 파일 또는 링크 결과물이 하나 이상 있어야 한다.

- 질문이 있으면 질문 수만큼 답이 존재해야 한다.
- 모든 답의 공백을 제거한 길이가 1 이상이어야 한다.

장애 대응 7단계

1단계: 증상을 한 문장으로 고정한다.
나쁜 기록: “로그인이 안 됨.”
좋은 기록: “운영 환경에서 학생 PIN을 5회 틀린 뒤 5분이 지나도 POST 로그인 요청이 429.”

2단계: 재현 조건을 기록한다.
사용자 역할, URL, 입력값의 종류, 시간, 브라우저, 운영/개발 환경을 구분한다.
실제 학생 개인정보와 비밀번호는 기록하지 않는다.

3단계: 계층을 구분한다.
- UI 문제: 요청이 발생하지 않거나 상태 표시만 잘못됨
- API 문제: 4xx/5xx 응답과 서버 로직
- DB 문제: 제약, 마이그레이션, 권한, 데이터 불일치
- 외부 서비스 문제: Supabase/OpenAI/스토리지/배포 플랫폼

4단계: 가장 좁은 증거를 수집한다.
- 브라우저 Console 오류 한 건
- Network의 URL, 메서드, 상태 코드, 응답
- 서버 로그의 같은 시간대 오류
- 관련 DB 행의 존재 여부와 제약
비밀키, 쿠키, 토큰, 학생 자유 기록은 공유하지 않는다.

5단계: 관련 코드를 요청 흐름 순서대로 읽는다.
화면 이벤트 -> api-client -> route.ts -> auth -> validator -> DB/외부 서비스 -> 응답 -> state.

6단계: 최소 수정 후 자동 검증한다.
npm run typecheck, npm test, npm run build 순으로 위험에 맞게 실행한다.
변경한 기능은 브라우저에서 정상·실패 경로를 모두 확인한다.

7단계: 회귀 범위를 확인한다.
공통 함수 변경이면 rg로 모든 호출부를 찾고 교사·학생 양쪽 문구와 동작을 확인한다.

HTTP 상태별 첫 확인 위치

- 요청 없음: 컴포넌트 이벤트와 브라우저 Console
- 400: validators와 비즈니스 조건
- 401: 세션 쿠키와 requireTeacher/requireStudentSession
- 403: requireTeacherClass/requireTeacherStudent, 역할 플래그
- 404: URL 매핑과 대상 id
- 409: 상태 충돌 조건과 중복 데이터
- 413: 파일 크기, 프록시·Vercel 제한
- 429: 로그인 잠금 또는 AI 사용량
- 500: 서버 로그, DB 오류, 마이그레이션, 외부 API

======================================================================
마지막 정리: 코드를 읽는 고정 순서
======================================================================

어떤 기능이든 다음 순서로 읽으면 길을 잃지 않는다.

1. 사용자가 누르는 버튼이나 제출 폼을 찾는다.
2. 이벤트 핸들러가 어떤 state를 바꾸는지 본다.
3. 호출하는 API URL과 HTTP 메서드를 기록한다.
4. 같은 경로의 app/api/**/route.ts를 연다.
5. 인증과 소유권 검사를 확인한다.
6. Zod 스키마와 비즈니스 규칙을 확인한다.
7. Supabase 테이블, 필터, 저장 순서를 확인한다.
8. 성공·실패 응답이 화면에서 어떻게 처리되는지 되돌아온다.
9. 같은 규칙을 검증하는 테스트와 마이그레이션을 찾는다.
10. AI 수정은 이 연결 중 하나라도 끊지 않았는지 검토한다.

모든 코드를 외울 필요는 없다. 중요한 능력은 “이 값이 어디에서 왔고, 누가
검증하며, 어디에 저장되고, 실패했을 때 무엇이 보이는가”를 끝까지 추적하는 것이다.
