HOW TO USE THIS GUIDE
======================================================================

This guide is not designed to make you memorize or rewrite every line of the
application. Its goal is to help you operate a real service, diagnose failures,
and verify changes produced by an AI coding assistant.

After completing the eight lessons, you should be able to:

1. Trace a user action from the browser to an API route and the database.
2. Separate browser, server, authentication, validation, and data failures.
3. Check whether an AI change fixes the root cause or only hides the symptom.
4. Review authorization, validation, error handling, and test coverage.
5. Follow a repeatable production-debugging process.

All examples come from the current project. File paths and line locations are
included so that you can compare the explanations with the real implementation.

PROJECT MAP

What the service does

Starlight Log is a school growth-record service for teachers and elementary
students. Students record emotions, complete learning reflections, view
evaluations, answer relationship surveys, exchange letters, earn badges, and
progress through a space-voyage reward system. Teachers manage classes and
students, review submissions, create evaluations, analyze relationships, and
generate AI-assisted growth reports. Administrator features manage accounts,
notices, settings, and AI usage.

Technology stack

- Next.js 14 App Router: pages and server API routes
- React 18: interactive user interfaces and state
- TypeScript: compile-time data contracts
- Supabase: PostgreSQL, teacher authentication, and storage
- Zod: runtime input and output validation
- bcryptjs: student PIN verification
- OpenAI SDK: growth, subject, and Holland reports
- Vitest: automated business-rule tests
- xlsx: spreadsheet-based student import

Important directories

app/                 Pages and API route handlers
components/          React components grouped by feature
lib/                 Auth, validation, database access, and business rules
lib/ai/              AI data preparation, prompts, validation, and storage
types/               Shared TypeScript types and constants
supabase/             Base schema and database migrations
tests/                Automated tests
public/               Static images and other public assets

Typical data flow

Browser UI
   |
   | fetch() through the shared API client
   v
Next.js API route: app/api/**/route.ts
   |
   | authentication -> validation -> business rules
   v
Supabase PostgreSQL, Storage, or OpenAI
   |
   | JSON response
   v
React state update -> screen re-render

When a feature fails, inspect this flow from left to right. Confirm that the
button handler ran, a request was sent, the API returned the expected status,
the database operation succeeded, and the returned data updated React state.

4. Interpreting status codes

File: lib/api-client.ts, lines 44-55

    const error = (json as { error?: unknown } | null)?.error;

    if (!res.ok) {
      if (typeof error === 'string') throw new Error(error);
      if (res.status === 413) throw new Error(tooLargeError);
      throw new Error(fallbackError);
    }

    if (json === null && text) throw new Error(fallbackError);
    return json as T;

- res.ok is true for HTTP status codes from 200 through 299.
- A string error returned by the route is converted into a JavaScript Error.
- Status 413 receives a specific file-size message.
- Unexpected failures receive a safe fallback message.
- A successful non-JSON response is treated as a contract failure.
- The final type assertion does not validate the response at runtime.

Status-code reference

- 200: successful read or update
- 201: successful creation
- 400: invalid input or business-rule violation
- 401: authentication is missing or credentials are incorrect
- 403: authenticated, but not allowed to access this resource
- 404: resource not found
- 409: operation conflicts with the current state
- 413: request body or upload is too large
- 429: too many attempts or usage limit exceeded
- 500: server, database, or external-service failure

Debugging sequence

1. Open the browser developer tools and inspect Console errors.
2. Open Network and confirm that the expected request exists.
3. Check the request URL, method, headers, and payload.
4. Check the response status and body.
5. If no request exists, inspect the React handler. If it exists, follow the
   matching API route.

AI change review

- Did the change remove or empty a catch block merely to hide an error?
- Can a failed response accidentally continue through the success path?
- Are JSON.stringify and Content-Type correct for the request type?
- Did the change apply application/json to FormData and break uploads?

3. Cleanup in finally

File: app/student/page.tsx, lines 471-477

      setError((err as Error).message);
      clearNoticeLater();
    } finally {
      setLoginLoading(false);
      setBootLoading(false);
    }

- catch converts a thrown error into visible UI state.

  the submit button.
- err as Error is a compile-time assertion, not runtime proof.

Common React failures

- Infinite requests: an effect dependency changes on every render.
- Stale screen: the server changed, but state was not updated or reloaded.
- Duplicate writes: a loading state does not disable repeated submissions.
- Login-screen flash: the UI renders before session checking finishes.
- Request race: an older slow response overwrites a newer fast response.

Debugging methods

- Inspect state with React Developer Tools.
- Compare request order and completion time in Network.
- Add temporary logs at loading start, response, catch, and finally.
- Remember that state setters affect a future render; logging immediately after
  a setter may still show the previous value.

AI change review

- Are loading flags cleared after both success and failure?
- Are required and optional asynchronous tasks correctly separated?
- Does the UI show success before required server work has finished?
- Did the change suppress an effect warning by deleting dependencies rather than
  fixing the underlying lifecycle problem?

3. safeParse inside the route

File: app/api/auth/student/login/route.ts, lines 12-20

export async function POST(req: Request) {
  const body = await req.json().catch(() => ({}));
  const parsed = studentLoginSchema.safeParse(body);

  if (!parsed.success) {
    return NextResponse.json(
      { error: parsed.error.flatten() },
      { status: 400 }
    );
  }
  const classCode = parsed.data.classCode.trim();

- Malformed JSON becomes an empty object and follows the validation path.
- safeParse returns a success/failure result instead of throwing.
- Invalid input stops before any database query occurs.
- Successful parsed.data is narrowed to the schema's inferred type.

TypeScript versus Zod

- TypeScript catches developer mistakes during editing and builds.
- Zod checks untrusted values received at runtime.
- api<ResponseType>() describes what the caller expects; it does not prove that
  the server returned that shape.
- Request bodies, AI output, imported spreadsheets, and JSONB values require
  runtime validation.

Failure patterns

- Input appears correct but returns 400: inspect whitespace, type conversion,
  maximum lengths, and regular expressions.
- Type checking passes but database insertion fails: compare code types with DB
  enums and column constraints.
- A shared schema change breaks several routes: search every import and caller.
- The UI displays [object Object]: the route returned a structured validation
  object while the API client expects a string error.

AI change review

- Was any introduced only to silence type errors?
- Is validation present on the server, not only in the browser?
- Do Zod limits match database column constraints?
- When an enum changes, were types, UI metadata, tests, and migrations updated?

Authentication design

- Teachers use Supabase Auth with email and password.
- Students use class code, name, and a four-digit PIN.
- Students receive a custom student_sessions token and cookie.
- Each flow uses different server helpers and cookie formats.

2. Creating a student session

File: lib/student-session.ts, lines 9-19

export async function createStudentSession(studentId: string) {
  const token = randomToken();
  const tokenHash = sha256(token);
  const expires = new Date();
  expires.setDate(expires.getDate() + EXPIRE_DAYS);

  const { error } = await supabaseAdmin.from('student_sessions').insert({
    student_id: studentId,
    token_hash: tokenHash,
    expires_at: expires.toISOString()
  });

- A cryptographically unpredictable token is created after login succeeds.
- Only the SHA-256 hash is stored in the database.
- The browser receives the original token.
- A database leak therefore does not immediately expose usable cookie tokens.
- The current expiry period is fourteen days.

4. Class ownership authorization

File: lib/auth.ts, lines 44-56

export async function requireTeacherClass(
  teacherId: string, classId: string
): Promise<NextResponse | null> {
  const { data } = await supabaseAdmin
    .from('classes')
    .select('id')
    .eq('id', classId)
    .eq('teacher_id', teacherId)
    .maybeSingle();

  if (!data) return NextResponse.json(
    { error: 'You do not have access to this class.' }, { status: 403 }
  );
  return null;
}

- Authentication proves which teacher is making the request.
- Authorization proves that the requested class belongs to that teacher.
- A logged-in teacher must not automatically access every class.
- supabaseAdmin can bypass Row Level Security, so application-level ownership
  checks are essential.

401 versus 403

- 401: the caller's identity is missing or invalid.
- 403: the identity is known, but the operation is not permitted.

Security debugging

- Missing cookie: inspect Set-Cookie and the browser Application panel.
- Production-only session failure: inspect HTTPS, secure, domain, and SameSite.
- Cross-class data exposure: check every route for ownership validation.
- Repeated student 401: inspect token hashes and expiry timestamps.
- Login loop: inspect /me handling and session-reset behavior.

AI change review

- Hiding a button in the UI is not server authorization.
- Never trust classId or studentId only because the browser supplied it.
- Never expose the service-role key through client code or NEXT_PUBLIC variables.
- Do not “fix” login by removing httpOnly or secure protections.

- students.class_id expresses class membership.
- on delete cascade removes dependent rows when the parent is deleted.
- NOT NULL and CHECK enforce rules even when application validation is bypassed.
- The current production structure is the base schema plus all later migrations.

Goals

1. Learning status is derived

File: lib/learning.ts, lines 30-35

export function getLearningStatus(
  submission: SubmissionStatusInput,
  grading?: GradingInput
): LearningStatus {
  if (!submission || submission.status !== 'submitted') return 'none';
  if (grading && grading.criteriaCount > 0) {
    return grading.gradedCount >= grading.criteriaCount ? 'reviewed' : 'grading';
  }
  return submission.feedback_text ? 'reviewed' : 'submitted';
}

- The four UI states do not map directly to one database column.
- No row or a draft produces none.
- Activities with criteria are reviewed only after every criterion is graded.
- Activities without criteria use the presence of narrative feedback.
- Teacher and student screens share this function, reducing disagreement.

2. Submission eligibility

File: lib/learning.ts, lines 114-123

export function isSubmittable(
  materialCount: number,
  questionCount: number,
  answers: (string | null | undefined)[],
): boolean {
  if (materialCount <= 0) return false;
  if (questionCount === 0) return true;
  if (answers.length < questionCount) return false;
  return answers.every(
    (answer) => (answer ?? '').trim().length > 0
  );
}

- At least one file or link is required.
- If there are no questions, the material alone is sufficient.
- Otherwise an answer must exist for every question.
- Whitespace-only answers are rejected.
- A pure function like this can be tested without a UI or database.

3. File validation

File: lib/learning.ts, lines 95-105

export function checkLearningFile(
  file: FileCheckInput, currentCount: number
): string | null {
  if (currentCount >= MAX_FILES_PER_SUBMISSION) {
    return `A maximum of ${MAX_FILES_PER_SUBMISSION} files is allowed.`;
  }
  if (!ALLOWED_MIME_TYPES.includes(file.type)) {
    return 'Only JPG, PNG, WEBP, and PDF files are allowed.';
  }
  if (file.size > MAX_FILE_BYTES) {
    return `Each file must be at most ${formatMb(MAX_FILE_BYTES)}.`;
  }
  return null;
}

- A valid file returns null; an invalid file returns a user-readable reason.
- Count, MIME type, and size are checked in order.
- Browser checks improve feedback, but the API must repeat the validation.
- The current 4 MB application limit stays below the hosting request limit.

  first failing step.
- For uploads, check size, Content-Type, multipart boundaries, and status 413.
- When a rule changes, search the shared helper, validator, route, labels, and
  tests together.

AI change review

- Was one business rule duplicated differently in the UI and API?
- Did state simplification remove an important distinction?
- Is the result of a mid-operation failure defined and recoverable?
- Did the change update only wording while leaving the server rule unchanged?

Seven-step incident process

Step 1: State the symptom precisely.

Weak: “Login does not work.”
Strong: “In production, student login continues returning 429 more than five
minutes after five incorrect PIN attempts.”

Step 2: Record the reproduction conditions.

Include role, URL, environment, browser, timing, and input category. Never record
real passwords, session cookies, or unnecessary student information.

Step 3: Identify the failing layer.

- UI: no request occurs or displayed state is incorrect.
- API: a 4xx or 5xx originates in route logic.
- Database: constraints, migration state, permissions, or records are wrong.
- External service: Supabase, OpenAI, storage, or hosting platform fails.

Step 4: Collect the smallest useful evidence.

- One relevant browser Console error
- Network URL, method, status, and sanitized response
- Server error from the same timestamp
- Existence and state of the relevant database row

Step 5: Read code in request order.

UI handler -> API client -> route -> authentication -> validation -> database or
external service -> response -> React state.

Step 6: Make the smallest safe change and verify it.

Run npm run typecheck, npm test, and npm run build according to risk. Manually
test both the success path and important failure paths.

Step 7: Review regression scope.

If a shared helper changed, search every caller. Check teacher and student flows,
language conventions, mobile layouts, empty data, and slow networks.

First place to inspect by symptom

- No request: React handler and browser Console
- 400: Zod validators and business rules
- 401: session cookies and authentication helpers
- 403: class/student ownership and feature roles
- 404: URL mapping and target ID
- 409: conflicting state or duplicate data
- 413: upload size and hosting limits
- 429: login lockout or AI usage limits
- 500: server logs, database errors, migrations, and external APIs

What to provide to an AI coding assistant

- Exact reproduction steps
- Expected result and actual result
- Sanitized Network status and response
- Relevant file paths
- Explicit out-of-scope areas
- Completion criteria: typecheck, tests, build, and manual scenarios

Final review checklist

Scope

[ ] Does the change solve the requested issue without a broad rewrite?
[ ] Does it preserve unrelated user changes?

Security

[ ] Does every write route authenticate on the server?
[ ] Is teacher ownership of the class or student verified?
[ ] Are service-role, OpenAI, and session secrets server-only?
[ ] Are passwords, tokens, and student records absent from logs?

Data

[ ] Is untrusted input validated with Zod or an equivalent check?
[ ] Is partial failure defined for multi-step writes?
[ ] Does every database change include a migration?
[ ] Were cascade-delete effects and recovery considered?

Asynchronous behavior and errors

[ ] Are required await operations present?
[ ] Are loading states cleared in finally?
[ ] Can a failed request accidentally look successful?
[ ] Does any catch block silently discard a critical error?

User experience

[ ] Is the message appropriate for the student or teacher audience?
[ ] Does an error message suggest a useful next action?
[ ] Does the screen work with empty data, mobile width, and slow networks?

Verification

[ ] Are normal, boundary, and failure cases covered?
[ ] Does npm run typecheck pass?
[ ] Does npm test pass?
[ ] Does npm run build pass?
[ ] Was the actual browser request and response inspected?

FINAL READING METHOD
======================================================================

Use this order whenever you study or debug a feature:

1. Find the button or form used by the user.
2. Find its event handler and state changes.
3. Record the API URL and HTTP method.
4. Open the matching app/api/**/route.ts file.
5. Verify authentication and ownership checks.
6. Inspect Zod validation and business rules.
7. Inspect Supabase tables, filters, and write order.
8. Return to the UI and inspect success and failure handling.
9. Find related tests and migrations.
10. Confirm that an AI-generated change did not break any connection in the
    chain.

You do not need to memorize the entire codebase. The essential skill is being
able to answer four questions: Where did this value come from? Who validates it?
Where is it stored? What does the user see when the operation fails?
