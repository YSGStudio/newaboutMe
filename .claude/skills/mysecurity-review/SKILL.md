# 보안 점검 (mysecurity-review)

내가 소유한 서비스를 **방어 목적으로** 점검한다. 목표는 "취약점 목록"이 아니라 **오늘 고칠 것과 나중에 결정할 것을 구분해주는 것**이다.

점검자는 대개 이 서비스를 혼자 만든 개발자다. 시간이 적고, 실제 사용자(여기서는 학생·교사 같은 실제 사람)의 데이터를 책임지고 있다. 그러니 이론적 위험을 길게 나열하는 것보다, **"이건 지금 남의 데이터가 새고 있다"와 "이건 나중에 봐도 된다"를 확실히 갈라주는 것**이 훨씬 가치 있다.

---

## 1단계 — 점검 방식을 먼저 묻는다

다른 어떤 작업보다 먼저, `AskUserQuestion`으로 이 질문을 한다. 방식에 따라 할 수 있는 일이 완전히 달라지고, 실서비스에 요청을 보내는 건 되돌릴 수 없기 때문에 임의로 정하지 않는다.

> 어떤 방식으로 보안 점검을 진행할까요?
> 1. 운영/Preview URL을 직접 테스트
> 2. 로컬 서버를 켜서 테스트
> 3. 로컬 코드만 점검

사용자가 요청에서 이미 방식을 분명히 밝혔다면(예: "로컬 코드만 봐줘", "https://... 여기 좀 봐줘") 되묻지 말고 **어떤 모드로 진행하는지 한 줄로 확인만 하고** 넘어간다. 애매하면 묻는다.

---

## 2단계 — 코드베이스 정적 검사 (모든 모드 공통, 항상 먼저)

동적 테스트를 하는 모드에서도 **정적 검사를 먼저 끝낸다.** 코드를 먼저 읽어야 어디를 찔러볼지 알 수 있고, 코드를 안 읽고 URL만 찔러보면 "겉으로 막혀 보이는" 것에 속는다. 정적 검사에서 나온 의심 지점이 곧 동적 프로브의 목록이 된다.

### 읽을 것

- **라우트** — 페이지 라우트와 API 라우트 전체 목록
- **권한 경계** — 인증 헬퍼, 미들웨어, 세션 처리
- **데이터 접근 패턴** — DB 클라이언트를 어떻게 만드는가, 권한을 우회하는 클라이언트(service role 등)를 쓰는 곳은 어디인가
- **환경변수 사용** — 서버 전용 값이 클라이언트로 새지 않는가
- **입출력** — 요청 바디에서 무엇을 받고 응답에 무엇을 담는가

전수 조사가 목표다. 라우트가 수십 개면 하나씩 열지 말고, 먼저 목록을 뽑고 → 권한 헬퍼를 호출하지 **않는** 라우트를 grep으로 걸러내 → 그 집합을 집중해서 읽는다. 구체적인 탐지 방법과 grep 패턴은 `references/static-checklist.md`에 있다. 정적 검사를 시작할 때 이 파일을 읽는다.

Next.js + Supabase 프로젝트라면 `references/nextjs-supabase.md`도 함께 읽는다. 이 스택에서 반복해서 터지는 함정(특히 service role 클라이언트가 RLS를 통째로 우회하는 문제)이 정리되어 있다.

### 두 관점으로 나눠서 정리한다

관점을 나누는 이유는 **대응 주체와 판단 기준이 다르기 때문**이다. 앞쪽은 "지금 사용자 데이터가 새는가"라 대개 즉시 코드를 고쳐야 하고, 뒤쪽은 "서비스가 망가지거나 돈이 새는가"라 대개 운영 정책과 비용 판단이 필요하다.

**사용자 권한 관점** — 남의 데이터에 접근할 수 있는가

- 인증·인가: 보호되어야 할 라우트가 실제로 로그인·역할을 확인하는가
- 소유자 확인: `id`를 파라미터로 받는 곳에서 "그 리소스가 요청자 것인지"를 확인하는가
- 관리자 접근: 관리자 페이지와 관리자 API가 역할까지 확인하는가 (UI만 숨긴 건 아닌가)
- 파일 접근: 업로드된 파일의 URL을 알면 남이 볼 수 있는가, 서명 URL의 만료가 있는가
- RLS: 정책이 켜져 있는가, 그리고 그 정책을 우회하는 경로가 있는가
- 입출력 필드 제한: 클라이언트가 보낸 필드를 통째로 DB에 넣지 않는가(권한 상승), 응답에 필요 없는 필드가 딸려 나가지 않는가

**우리 서비스 관점** — 서비스와 비용이 안전한가

- API 키·환경변수 노출: 클라이언트 번들과 저장소 커밋에 비밀값이 들어갔는가
- 오류 응답: 에러가 스택 트레이스·쿼리·내부 경로를 그대로 보여주는가
- rate limit과 과금 상한: 외부 유료 API(AI 등)를 호출하는 엔드포인트에 호출 상한이 있는가
- 환경 분리: 개발과 운영이 같은 DB·같은 키를 쓰고 있지 않은가
- 백업·복구: 백업이 실제로 돌고 있는가, 복구를 해본 적이 있는가
- 사고 대응: 키가 유출됐을 때 무엇을 어떤 순서로 교체할지 정해져 있는가

각 항목은 "확인함 / 문제 있음 / 확인 불가"로 결론을 낸다. **확인하지 못한 항목을 통과로 적지 않는다.** 확인 불가는 그 자체로 유용한 정보다 — 3단계 결과의 "반복 점검할 것"으로 넘어간다.

---

## 3단계 — 모드별 동적 점검

### 모드 1: 운영/Preview URL을 직접 테스트

요청을 보내기 전에 **반드시 두 가지를 확인받는다.**

1. 이 URL이 사용자 소유인가
2. 지금 점검해도 되는가 (운영 중이라면 시점이 괜찮은가)

이건 형식적인 절차가 아니다. 남의 서버에 보안 프로브를 보내는 건 권한 없는 접근이고, 운영 중인 서비스에 보내는 요청은 실제 사용자에게 영향을 준다. 사용자가 확인해주기 전에는 요청을 보내지 않는다. 확인이 애매하면 모드 2나 3을 권한다.

확인이 끝나면 `curl` 또는 브라우저로 **비파괴 요청만** 보낸다. 프로브 목록과 명령 예시는 `references/dynamic-probes.md`에 있다.

### 모드 2: 로컬 서버를 켜서 테스트

프로젝트의 dev 서버를 백그라운드로 띄우고(`npm run dev` 등), 준비될 때까지 기다린 뒤 `http://localhost:<port>` 기준으로 모드 1과 **같은 프로브**를 보낸다. 소유 확인은 필요 없다.

단, 로컬이 어떤 DB를 보고 있는지 먼저 확인한다. `.env.local`이 운영 DB를 가리키고 있으면 "로컬 테스트"가 사실상 운영 데이터 접근이다. 이 경우 사용자에게 알리고 모드 1의 확인 절차를 따른다.

점검이 끝나면 띄운 서버를 정리한다.

### 모드 3: 로컬 코드만 점검

**실제 HTTP 요청을 보내지 않는다.** 대신 정적 검사에서 나온 의심 지점을 두 가지로 바꿔서 낸다.

- **위험 후보**: "이 라우트는 소유자 확인이 없어 보인다" — 근거가 되는 파일·줄과 함께
- **작성해야 할 실패 테스트**: 지금 실행하면 **실패해야 정상인** 테스트. 즉 "이렇게 요청하면 403이 나와야 하는데 지금은 200이 날 것 같다"를 코드로 적어둔 것. 나중에 모드 1·2로 넘어가거나 자동화 테스트에 넣을 때 그대로 쓸 수 있게 구체적인 요청 형태로 쓴다.

---

## 동적 점검의 범위 — 여기까지만

동적 점검은 **아래 6가지로 제한한다.** 이 범위를 정한 이유는, 이것들이 "실제로 데이터가 새는가"를 확인하는 가장 짧은 경로이면서 서비스에 해를 주지 않기 때문이다. 이 범위를 넘어서면 얻는 정보에 비해 위험이 급격히 커진다.

1. 비로그인 상태로 보호 페이지·API 접근
2. 일반 사용자 계정으로 관리자 경로와 관리자 API 접근
3. `id`나 경로를 남의 것으로 바꿔서 접근
4. private 파일의 직접 URL 접근
5. 오류 응답에 민감 정보가 나오는지 확인
6. 가벼운 rate limit 확인 (연속 몇 회 수준)

**하지 않는 것:**

- 대량 요청, 부하 테스트, 무차별 대입
- 파괴적 요청 — `DELETE`, 그리고 실제로 상태를 바꾸는 `POST`/`PATCH`/`PUT`
- 실제 데이터 변경 (테스트 계정이라도, 사용자가 따로 허락하지 않았다면)

권한 확인은 대부분 **읽기 요청과 응답 코드만으로** 판별된다. 쓰기가 막혔는지 보고 싶으면 실제로 쓰지 말고, 인증 없이 보낸 쓰기 요청이 `401`/`403`으로 끊기는지만 본다 — `200`이 돌아왔다면 그때는 이미 데이터가 변경된 것이므로, 사용자에게 즉시 알리고 되돌릴 방법을 함께 정리한다.

경계에 걸리는 요청이 필요해지면 혼자 판단하지 말고 사용자에게 묻는다.

## 결과 형식

항상 이 세 갈래로 낸다. 심각도 라벨(Critical/High/…)로 나누지 않는 이유는, 혼자 운영하는 서비스에서 실제로 필요한 판단이 "심각도"가 아니라 **"내가 지금 뭘 해야 하나"**이기 때문이다.

```markdown
# 보안 점검 결과

**점검 방식**: (모드) · **점검 대상**: (URL 또는 로컬 경로) · **일시**: (날짜)

## 바로 고칠 것
지금 데이터가 새고 있거나, 고치는 데 판단이 필요 없는 것.

### 1. (한 줄 요약)
- **위치**: `파일:줄` (동적으로 확인했다면 요청과 응답 코드도)
- **문제**: 무엇이 잘못됐는지
- **영향**: 누가 무엇을 볼 수 있는지 / 무엇이 망가지는지
- **수정**: 구체적인 방법

## 사람이 결정할 것
비용·정책·UX 트레이드오프가 걸려 있어 내가 정하면 안 되는 것.

### 1. (한 줄 요약)
- **상황**: 지금 상태
- **선택지**: A안 / B안과 각각의 대가
- **추천**: 어느 쪽을, 왜

## 반복 점검할 것
한 번 고치고 끝나지 않는 것. 확인하지 못한 항목도 여기로.

- [ ] (항목) — (주기 또는 계기) — (확인 방법)

## 점검 못 한 것
(모드 제약이나 접근 권한 때문에 확인하지 못한 범위. 빈칸이면 생략)
```

각 항목은 **재현 가능하게** 쓴다. "인증이 약함" 같은 말은 쓸모없다. "`GET /api/students/{남의id}`에 학생 세션 쿠키로 요청하면 200과 함께 이름·생년월일이 반환된다"처럼 쓴다.

발견이 없으면 없다고 분명히 쓴다. 채우기 위해 사소한 것을 부풀리지 않는다 — 진짜 문제가 묻힌다.

---

## 함께 지킬 것

- **근거 없는 단정 금지.** 코드에서 확인한 것과 요청으로 확인한 것을 구분해서 쓴다. 정적 검사만으로는 "취약해 보인다"까지가 정직한 표현이다.
- **찾은 것을 자동으로 고치지 않는다.** 보안 수정은 권한 로직을 건드리는 일이라 잘못 고치면 멀쩡한 사용자가 막힌다. 결과를 먼저 내고, 고칠지는 사용자가 정한다. (사용자가 고쳐달라고 하면 그때 고친다.)
- **비밀값을 결과에 그대로 붙여넣지 않는다.** 노출된 키를 발견하면 위치와 앞 4자리 정도만 적는다. 결과 문서가 또 하나의 유출 경로가 되면 안 된다.
- 실제로 유출된 키를 발견하면 그건 언제나 "바로 고칠 것"이고, 수정은 코드 변경이 아니라 **키 교체**부터다.
